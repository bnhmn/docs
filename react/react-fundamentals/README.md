# React with Vite

This guide shows how to set up a new [React](https://react.dev/) app with [Vite](https://vite.dev/).

## 1. Create a React project using Vite

Run the following command:

```bash
npm create vite@latest my-project-name
```

It will output something like this:

```bash
√ Select a framework: » React
√ Select a variant: » TypeScript
√ Which linter to use? » Oxlint
√ Install with npm and start now? » Yes
```

To run the application:

```bash
npm run dev
```

To build the application for production:

```bash
npm run build
```

## 2. Formatting and linting with Biome

Remove the `.oxlintrc.json` file generated by Vite and uninstall `oxlint`:

```bash
npm uninstall -D oxlint
```

Install [Biome](https://biomejs.dev/installation/quick-start/):

```bash
npm install -D -E @biomejs/biome
```

Create a configuration with `npx biome init`, or use this project's [Biome preset](biome.json).

Add these scripts to `package.json`:

```json
{
  "scripts": {
    "fix": "biome check --write",
    "ci:check": "biome ci"
  }
}
```

Run `npm run fix` to format files and apply safe fixes. Run `npm run ci:check` to check the project
without modifying files.

## 3. Run checks before commits with Lefthook

<!-- prettier-ignore -->
> [!IMPORTANT]
> Tools like Lefthook and Husky let you run checks automatically before each Git commit.
> This setup works only when the npm project is at the root of the Git repository.
> Otherwise, it cannot reliably activate the hooks.

Install [Lefthook](https://lefthook.dev) as a development dependency:

```bash
npm install -D lefthook
```

The package normally activates its Git hooks during installation. If npm postinstall scripts are
disabled, activate the hooks manually with `npx lefthook install`.

Create `lefthook.yml` in the project root:

```yaml
# https://lefthook.dev
pre-commit:
  parallel: true
  jobs:
    - name: Fix code
      run: npx biome check --write {staged_files}
      stage_fixed: true
```

This formats and checks staged files, then stages any fixes.

## 4. Test React components

After implementing the UI, add component tests to ensure that the UI behaves as expected.

### Setup

#### Dependencies

```bash
npm install -D vitest jsdom @vitest/coverage-v8 @testing-library/react @testing-library/jest-dom @testing-library/user-event
```

[Vitest](https://vitest.dev/) is a popular testing framework. The
[React Testing Library](https://github.com/testing-library/react-testing-library) is a lightweight
solution for testing React components that encourages better testing practices.
[jsdom](https://github.com/jsdom/jsdom) is a a Node.js implementation of various web standards, with
the goal to emulate enough of a subset of a web browser to be useful for testing.

#### package.json

Add these scripts to your `package.json` file:

```json
{
  "scripts": {
    "test": "vitest",
    "ci:test": "vitest run --coverage"
  }
}
```

#### tsconfig.node.json

Extend your `tsconfig.node.json` file:

```jsonc
{
  "compilerOptions": {
    // Enable jsx in test folder
    "jsx": "react-jsx",

    // https://github.com/testing-library/jest-dom#with-vitest
    "types": ["vitest/globals", "@testing-library/jest-dom"],
  },
  "include": ["vite.config.ts", "vitest.*.ts", "test"],
}
```

#### vite.config.ts

Save this `vite.config.ts` file in your project root:

```ts
import react from "@vitejs/plugin-react";
import { defineConfig } from "vitest/config";

// https://vite.dev/config/
export default defineConfig({
  plugins: [react()],
  test: {
    environment: "jsdom",
    setupFiles: ["./vitest.setup.ts"],
    // Speed up tests: components are loaded once per worker, not once per file; tests stay isolated
    pool: "vmThreads",
    // Measure test coverage
    coverage: {
      provider: "v8",
      include: ["src/**/*.{ts,tsx}"],
      exclude: ["src/**/generated/**", "src/**/*.gen.ts"],
      reporter: ["text", "lcov"], // SonarQube reads "lcov"
    },
  },
});
```

#### vitest.setup.ts

Save this `vitest.setup.ts` file in your project root.

```ts
// https://github.com/testing-library/jest-dom#with-vitest
import "@testing-library/jest-dom/vitest";
import { cleanup } from "@testing-library/react";
import { afterEach } from "vitest";

// https://testing-library.com/docs/react-testing-library/setup/#auto-cleanup-in-vitest
afterEach(() => {
  cleanup();
});
```

### Create and run tests

Create the following test:

```tsx
// test/App.test.tsx
import { describe, expect, it } from "vitest";
import { userEvent } from "@testing-library/user-event";
import { render, screen } from "@testing-library/react";
import App from "../src/App.tsx";

describe("App", () => {
  it("should render the app", async () => {
    const user = userEvent.setup();
    render(<App />);

    await user.click(screen.getByRole("button"));

    expect(screen.queryAllByRole("heading")[0]).toHaveTextContent("Get started");
  });
});
```

and run `npm test` to execute it.

### Structure Tests with Reusable Fixtures

A test fixture, also known as a test data builder, creates reusable test data with sensible
defaults, making tests clearer and easier to maintain.

For example, this component displays songs in a playlist:

```tsx
// src/components/Playlist.tsx
export type Song = {
  id: number;
  title: string;
  artist: string;
};

type PlaylistProps = {
  songs: Song[];
  onPlay: (song: Song) => void;
};

export function Playlist({ songs, onPlay }: PlaylistProps) {
  if (songs.length === 0) {
    return <p>No songs in the playlist</p>;
  }
  return (
    <ul aria-label="Playlist">
      {songs.map((song) => (
        <li key={song.id}>
          <span>
            {song.title} — {song.artist}
          </span>
          <button type="button" onClick={() => onPlay(song)}>
            Play {song.title}
          </button>
        </li>
      ))}
    </ul>
  );
}
```

This test fixture provides a default song and allows individual tests to override its fields:

```ts
// test/support/song-fixtures.ts
import type { Song } from "../../src/components/Playlist";

export function aSong(overrides: Partial<Song> = {}): Song {
  return {
    id: 1,
    title: "Here Comes the Sun",
    artist: "The Beatles",
    ...overrides,
  };
}
```

The following tests use the song fixture to test the playlist component:

```tsx
// test/components/Playlist.test.tsx
import { render, screen } from "@testing-library/react";
import userEvent from "@testing-library/user-event";
import { describe, expect, it, vi } from "vitest";
import { Playlist, type Song } from "../../src/components/Playlist";
import { aSong } from "../support/song-fixtures";

describe("Playlist", () => {
  function renderPlaylist(songs: Song[] = [aSong()]) {
    // Render fixture: shared component rendering, mock setup, and common lookup helpers.
    const user = userEvent.setup();
    const onPlay = vi.fn<(song: Song) => void>();
    render(<Playlist songs={songs} onPlay={onPlay} />);
    return {
      user,
      onPlay,
      songList: () => screen.queryAllByRole("listitem"),
      playButton: (title: string) => screen.getByRole("button", { name: `Play ${title}` }),
    };
  }

  const song1 = aSong();
  const song2 = aSong({ id: 2, title: "Yellow Submarine" });

  it("shows songs in the supplied order", () => {
    const { songList } = renderPlaylist([song1, song2]);
    const songs = songList();

    expect(songs).toHaveLength(2);
    expect(songs[0]).toHaveTextContent(song1.title);
    expect(songs[1]).toHaveTextContent(song2.title);
  });

  it("plays the selected song", async () => {
    const { user, onPlay, playButton } = renderPlaylist([song1, song2]);

    await user.click(playButton(song2.title));

    expect(onPlay).toHaveBeenCalledWith(song2);
  });

  it("shows an empty state when there are no songs", () => {
    const { songList } = renderPlaylist([]);

    expect(songList()).toHaveLength(0);
    expect(screen.getByText("No songs in the playlist")).toBeVisible();
  });
});
```

## 6. Vite configuration and environment variables

### Modes and env files

Vite loads shared values from `.env` and mode-specific values from files such as `.env.development`
and `.env.production`. The dev server uses development mode, builds use production mode, and Vitest
uses test mode by default. Define the same variable in each file to use a different value per mode.
See [Vite Env Variables and Modes](https://vite.dev/guide/env-and-mode).

### Reading variables in the app

Read client-side variables through `import.meta.env`:

```ts
const apiUrl = import.meta.env.VITE_API_URL;
```

Only variables with the `VITE_` prefix are exposed to browser code, and values are strings. Do not
put secrets in them.

### Build-time values

Vite embeds these values in the client bundle when building. To select a different env file, pass a
mode, for example `npm run build -- --mode development`. This loads the development config but still
creates a production build.

## 7. Vite proxy for API requests during development

When you run `npm run dev`, the Vite dev server can forward requests to another server. This lets
the browser send requests to the same origin as the app while Vite forwards them to a REST API. It
avoids development-time CORS errors without changing the API's CORS settings.

Add a proxy rule to `vite.config.ts`:

```ts
export default defineConfig({
  server: {
    proxy: {
      "/api": {
        target: "http://localhost:8080",
        changeOrigin: true,
      },
    },
  },
});
```

Requests to `/api/**` are forwarded to `http://localhost:8080/api/**`. In the app, use a relative
URL such as `fetch("/api/users")`.

Note that the proxy only applies to the Vite development server, and is not included in the
production build. So make sure to configure the production web server or API separately. See
[Vite server proxy options](https://vite.dev/config/server-options#server-proxy).

## 8. Developer Guide

You should include a developer guide like this in the README of every React project so that new
developers can quickly find their way around.

### Quick Start

1. Ensure [Node.js](https://nodejs.org/en) is installed on your machine.
2. Run `npm ci` to install the dependencies.
3. Run `npm run dev` to start the development server.

### Commands

- `npm test` - execute tests
- `npm run build` - build production bundle
- `npm run fix` - format code and fix code style
- `npm run ci:check` - check formatting and lint rules without modifying files
